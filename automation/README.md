## Message and account rules

The [30 October audit](AUDIT.md) records verified production behavior, parser/readiness fixes and the remaining mailbox checks. The reviewed worker fixes and sequential Gmail workflow, including Spam scanning, are now deployed. The existing Gmail workflow ID and credential bindings are preserved. The owner-selected request-only forwarding policy below supersedes the earlier authentication blocker; a real login-to-card test remains to be completed.

`MAILBOXES` contains one entry, for example `central-gmail`, with `provider: "gmail"`. Its optional `trustedForwarders` list contains only owner-confirmed source addresses, with a maximum of four. The two active Hotmail addresses are now configured privately on the VM; the central Gmail itself is not a forwarder. The example environment leaves this list empty. Confirm additional addresses before adding them. An allowlisted address does not bypass authentication checks.

Every accepted message must identify exactly one Steam **username** in the email content and match exactly one currently assigned account returned by Field Desk. Recipient address is never a fallback for a forwarded message or for an unknown central recipient. A missing or ambiguous username is an exception; the worker must never guess a store.

Production uses `requestOnly: true` and `allowRequestedRedirects: true` in the central mailbox's `MAILBOXES` object. The owner explicitly chose to read the existing Hotmail Redirects even when Gmail reports failed original sender authentication. For this route the visible From must be exactly Steam's sender, To must contain exactly one confirmed source address, and the **body** must identify the Steam username in an active, correctly signed Field Desk request. This is an owner-trusted forwarding route, not proof of original Steam authentication. The same username must match one currently assigned Field Desk account. Missing, ambiguous, expired or future-dated messages are rejected. Recipient is a source constraint, never the account lookup key.

Without that explicit option the original strict authentication policy remains. Authenticated wrapped forwards still require original Steam From and dated forwarding markers. Every route requires one five-character uppercase alphanumeric code and the original message Date; arrival in Gmail cannot renew an old code. No code or password is logged or saved in worker state.

## Polling and delivery

**Get code in Field Desk → search recent central Gmail mail for that username → deliver to its assigned store.** The existing n8n timer checks the worker every 15 seconds, but does not read Gmail while idle. A signed `steam.otp.requested` event opens a separate ten-minute account window. The next tick searches recent matching mail, including already-read messages and Spam, using `includeSpamTrash=true` and `-in:trash`. It checks every 15 seconds until a fresh code is delivered or the window expires. Request-only mode has no broad background inbox scan. Pressing Get code does not log in to Steam or generate an email; the Steam login generates it.

Only the requested body username can deliver. A successful delivery closes that account's window, including when the fresh email arrived before the button press. Other accounts retain their own windows. Duplicates are marked read without posting again. Failures leave mail available for a bounded retry, and expiry is rechecked after API lookup.

Flow: signed request → central Gmail list → full matching message → worker source/date/body-username/code checks → GET `/steam/accounts` → POST `/steam/otp` with an idempotency key → mark read. The small Node worker stores hashes, request/poll times and sanitized issue reasons, with no OTP bodies. See [CONTRACT-NOTES.md](CONTRACT-NOTES.md).

## Central Gmail setup

1. Confirm the central Gmail account and the exact active forwarding addresses with the owner. Add only confirmed addresses to `trustedForwarders`. Set a stable central mailbox ID; it is part of the delivery deduplication namespace.
2. Import the central Gmail workflow and set its `MAILBOX ID` to the configured ID. Create **one** Google OAuth credential for the central inbox and bind it to its Gmail nodes. Gmail API modify scope is needed to read messages and mark them read. For a Google app in testing, add the central account as a test user and resolve consent/token expiry before unattended polling.
3. Bind the **OTP Worker** credential to worker HTTP nodes. Set `requestOnly: true` and `allowRequestedRedirects: true` in the central mailbox object for the owner-selected redirect policy. Keep exact forwarding source addresses private. On the existing VM, `python3 automation/scripts/enable-requested-redirects.py` backs up and updates only this policy, preserving every secret and existing mailbox ID.
4. Recreate the worker after code/policy changes and publish the existing Gmail workflow. The owner then presses Get code for an assigned account and performs a Steam login. Check the code appears on the correct store card without copying it into chat. Test each source and both login/new-device layouts; no direct Hotmail OAuth credential is used.

For this VM, the owner signed in to Google Cloud and a dedicated **Field Desk Steam OTP** project was created with Gmail API enabled. The owner accepted Google's User Data Policy, created the OAuth web client, entered its values privately into n8n and approved Gmail access. n8n displayed **Account connected** with no pending Save change; saved credential metadata was independently verified. That credential is bound to all three Gmail API nodes in the delivery workflow. The callback is `https://n8n.129-225-72-140.sslip.io/rest/oauth2-credential/callback`. **Central Gmail mailbox** uses custom scope `https://www.googleapis.com/auth/gmail.modify` and HTTP Request access restricted to `gmail.googleapis.com`. Google Testing mode requires the central Gmail as a test user and normally expires its consent/tokens after seven days; finish the long-term Google app setup before unattended event use.

`C-gmail-header-check.json` is a manual, read-only connection diagnostic. It checks at most five recent Steam messages, including Spam, and requests only Authentication-Results, ARC-Seal, ARC-Authentication-Results, ARC-Message-Signature, From, To and Date headers. Its explicit partial response excludes snippets, subjects and bodies. Its last node emits booleans/counts only; intermediate headers must be reviewed privately. It never marks mail read or calls the worker/Field Desk. These flags are diagnostics, not permission to accept unauthenticated mail. On the 1 GB VM, run this check in the existing n8n editor; do not start a second n8n CLI execution alongside the production service.

The first real check found conflicting authentication results, so diagnostic pass flags now use exactly one receiving `mx.google.com` header, never another server's pass result. The expanded check read five messages: two direct messages had Steam-aligned Google DMARC pass; three Hotmail Redirect messages had Google DMARC fail and ARC pass. Those three had Microsoft ARC instance 1 followed by Google's instance 2, but Microsoft's sealed results reported SPF, DKIM and DMARC **none**, with no Steam domain attestation. Microsoft's message signature also omitted To. A valid chain therefore does not establish original Steam authentication. The initial strict policy therefore blocked these redirects. The owner subsequently selected the request-only trusted forwarding policy above: it does not require an original DMARC/ARC pass and does not claim one. No account email changes or direct Outlook connection are needed.

The signed request webhook is `/webhook/steam-request` after the workflow is active. It forwards the raw request body to the worker, which checks `X-FieldDesk-Signature: sha256=<HMAC-SHA256>` and stores a ten-minute account-name polling window. Invalid signatures do not change polling. The webhook is a search hint; the automation never signs in to Steam.

Both instance and workflow settings avoid saving execution payloads, but manual editor runs may display transient email content. Do not pin real data or enable payload logging.
